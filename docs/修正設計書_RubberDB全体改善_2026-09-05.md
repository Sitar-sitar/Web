## 1. 結論

現時点で、RubberDB の本番公開サイトに対して **直ちに侵害へつながる Critical（P0）の問題や、ハードコードされた秘密鍵・APIトークンの本番流出は確認していない**。

ただし、次の項目は優先度 P1 として修正を推奨する。

1. **Vite 7.1.9 の既知の高重要度脆弱性と、`--host` / `server.host: true` の組み合わせ**
2. **Manus Debug Collector が開発時に認証情報を含む通信ログを保存し得る設計、およびログ受付エンドポイントの制限不足**
3. **本番 HTML に未解決の Analytics プレースホルダが残っている**
4. **favicon が本番で存在しない `/manus-storage/...` を参照している**
5. **オープン価格商品の価格計算・予算判定が不整合**
6. **CI/CD に TypeScript 検査・テスト・依存脆弱性検査・成果物検査がない**
7. **未使用テンプレート／依存パッケージが多く、既知脆弱性を含む不要な依存が残っている**

セキュリティ面では、RubberDB は現在 GitHub Pages 上の静的サイトであり、ログイン・サーバーサイドDB・状態変更APIを持たないため、SQL Injection、CSRF、サーバー認証回避などの攻撃面は現構成では小さい。一方、**ローカル開発環境と依存サプライチェーンが相対的に大きなリスク面**になっている。

# 5. 詳細設計

## SEC-01 — Vite 7.1.9 の既知脆弱性

**優先度: P1 / High**

### 現状

`pnpm-lock.yaml` および最新 GitHub Actions ログで Vite `7.1.9` を確認。

さらに、以下の両方が設定されている。

- `package.json`: `vite --host`
- `vite.config.ts`: `server.host: true`

これは Vite の 2026年公開アドバイザリが影響条件として挙げる「開発サーバーをネットワークへ明示公開」に該当する。

確認済みアドバイザリ:

- GHSA-p9ff-h696-f583 — Arbitrary File Read via Vite Dev Server WebSocket
  - Vite 7.x affected: `>=7.0.0 <=7.3.1`
  - fixed: `7.3.2`
- GHSA-v2wj-q39q-566r — `server.fs.deny` bypassed with queries
  - Vite 7.x affected: `>=7.1.0 <=7.3.1`
  - fixed: `7.3.2`
- GHSA-fx2h-pf6j-xcff — Windows alternate path による `server.fs.deny` bypass
  - Vite 7.x affected: `>=7.0.0 <=7.3.4`
  - fixed: `7.3.5`

したがって **7.1.9 は3件とも影響範囲内**。

### 影響

GitHub Pages の本番静的ファイルが直接この脆弱性を受けるわけではない。

しかし、ローカル PC や検証環境で `pnpm dev` を実行し、LAN・VPN・共有ネットワーク等からアクセス可能になっている場合、開発端末内ファイルの読み取りにつながる可能性がある。

### 修正設計

1. Vite を **最低 7.3.5 以上**へ更新する。
2. 実装時点で Vite Security Advisories を再確認し、可能なら最新のサポート版へ上げる。
3. 通常の `dev` は loopback のみとする。
   - `vite`
   - または `host: "127.0.0.1"`
4. LAN公開が必要な場合だけ別スクリプトを用意する。
   - 例: `dev:lan`
5. `server.fs.deny` は防御補助として維持するが、旧 Vite のまま deny 設定だけで防げるとは考えない。

### 完了条件

- `pnpm exec vite --version` が修正版以上
- 通常 `pnpm dev` が他端末から接続不能
- LAN公開は明示コマンド実行時のみ

## SEC-02 — Manus Debug Collector のログ収集設計

**優先度: P1 / High（開発環境）**

### 現状

`vite.config.ts` の開発用プラグインは `/__manus__/logs` へブラウザログを POST し、以下をローカルファイルへ記録する。

- console
- network request / response
- UI events
- input 値
- session events

`debug-collector.js` では sensitiveFields に `authorization` 等が定義されているが、Fetch の request header を `Object.fromEntries(new Headers(...).entries())` した後、**ヘッダー単位の明示的な redaction を行わずログエントリへ格納している**。

また `vite.config.ts` の `/__manus__/logs` は:

- 認証なし
- Origin チェックなし
- Content-Length 上限なし
- body を文字列へ蓄積してから `JSON.parse`

という構成。

### 影響

開発サーバーをネットワーク公開した場合:

- Authorization / API-Key / Cookie 系情報のログ保存リスク
- 大きな POST によるメモリ・ディスク消費
- 他サイトから開発サーバーへ到達可能な環境でのログ汚染

が考えられる。

現時点の RubberDB 本体は認証通信を行っていないため、**現在の本番ユーザー情報が漏れているという意味ではない**。

### 修正設計

Debug Collector を残す場合:

1. デフォルト OFF にする。
2. `MANUS_DEBUG=1` 等を明示した場合だけ有効化。
3. request / response headers は **allowlist 方式**に変更。
   - 許可例: `content-type`, `accept`
   - 原則ログ禁止: `authorization`, `cookie`, `set-cookie`, `x-api-key`, `proxy-authorization`
4. request / response body の記録をデフォルト無効化。
5. `/__manus__/logs` に最大リクエストサイズを設定。
   - 例: 256 KB 程度
6. localhost 以外からの受付を拒否、または Origin を厳格確認。
7. ログファイルへの書き込み前にもサイズを検査する。

RubberDB で不要なら **機構自体を削除する方が望ましい**。

### 完了条件

- 通常開発では collector がロードされない
- Authorization/Cookie/API key がログへ残らないテストがある
- 大容量 POST が 413 等で拒否される

## CI-01 — 品質・セキュリティゲート不足

**優先度: P1 / High**

### 現状

RubberDB の Pages build は実質:

1. `pnpm install --frozen-lockfile`
2. `pnpm exec vite build --base /Web/rubber/`
3. Pages artifact へコピー

のみ。

`package.json` には `check: tsc --noEmit` があるが、Pages workflow では実行していない。

テスト・lint・audit・成果物検証もない。

実際、最新 build は成功しているにもかかわらず、Vite は以下を警告している。

- `%VITE_ANALYTICS_ENDPOINT% is not defined`
- `%VITE_ANALYTICS_WEBSITE_ID% is not defined`

つまり **build success = 正常な本番成果物ではない**。

### 修正設計

Pages workflow の RubberDB build 前後に次を追加する。

#### Build 前

- `pnpm check`
- unit tests
- ラバーデータ整合性テスト
- dependency vulnerability check

#### Build 後

成果物に対し以下が存在したら失敗:

- `%VITE_`
- `/manus-storage/`
- `__manus__/`
- source map（公開しない方針なら）
- 想定外の `.env` / `.log`

さらに:

- `index.html` に `/Web/rubber/assets/...` が存在すること
- favicon が実在すること
- bundle size が閾値を超えていないこと

### 完了条件

警告を無視して成功させず、不完全な Pages artifact を CI が自動検出する。

## CI-02 — RubberDB デプロイが HoYoverse に結合

**優先度: P2 / Medium**

### 現状

`RubberDB` push 時の workflow は、`hoyoversebuilder` ブランチ側の `deploy-pages.yml` を dispatch する。

その combined workflow は RubberDB をデプロイする前に:

- HoYoverse dependency install
- HoYoverse API build
- Railway API health check
- HoYoverse build

を行う。

### 問題

RubberDB だけを変更した場合でも、HoYoverse API 障害や HoYoverse build failure によって RubberDB の公開が止まる。

### 修正設計

Pages は最終的に1つの artifact が必要なため、デプロイ自体は統合してよいが、ビルド責務を分離する。

推奨案:

- `build-rubber` job
- `build-hoyoverse` job
- `assemble-pages` job
- `deploy` job

RubberDB変更時に HoYoverse API のオンライン疎通を必須にするかは再検討する。

最低でも、どちらのサブサイトが原因で失敗したかを明確にする。

## APP-01 — オープン価格が合計 0 円として扱われる

**優先度: P1 / High（表示正確性）**

### 現状

`Rubber.price` は `number | null`。

合計価格:

```ts
const total = (fore.price ?? 0) + (back.price ?? 0);
```

その結果、オープン価格の商品は **合計上 0 円**として扱われる。

画面ではその数値を:

`両面の参考価格合計（税込）`

として表示する。

### 影響

- 片面がオープン価格 → 合計が過少表示
- 両面がオープン価格 → `¥0` になり得る

### 修正設計

価格の「不明」と「0円」を区別する。

推奨ドメイン設計:

```text
knownPriceTotal: number
hasUnknownPrice: boolean
```

表示仕様:

- 2枚とも価格あり → `¥12,100（税込）`
- 1枚以上 open price → `合計算出不可（オープン価格を含む）`
- 必要なら既知分のみ `確認できる価格分: ¥6,050 + オープン価格`

### 完了条件

`price === null` を0円として表示しない。

## APP-02 — 予算判定だけ `null = 12,000円` 扱い

**優先度: P1 / High（推薦ロジック）**

### 現状

```ts
function priceOf(rubber: Rubber) {
  return rubber.price ?? 12000;
}
```

予算フィルタではオープン価格を 12,000 円として扱う一方、APP-01 の合計では 0 円として扱う。

同一の `price: null` が:

- 予算判定: 12,000円
- 合計表示: 0円

という相反する意味を持っている。

### 修正設計

`null` にダミー価格を割り当てない。

予算条件の仕様を明示する。

推奨:

- 「6,000円まで」「8,000円まで」では **価格不明商品を除外**
- UI に「オープン価格の商品は予算指定時の候補から除外」と明記
- 「こだわらない」では候補に含める

市場価格を扱いたい場合は別フィールドとして管理し、公式価格と混同しない。

が固定文字列として残る。

### 修正設計

データに確認日を持たせる。

```text
verifiedAt: YYYY-MM-DD
```

またはデータセット単位:

```text
DATASET_VERIFIED_AT
```

ただし一部だけ更新されるため、**商品単位の `verifiedAt` が最も正確**。

UI はデータから表示する。

## DATA-02 — ラバーデータの自動整合性検査がない

**優先度: P1 / High**

### 対象

`client/src/lib/rubberData.ts`

### 追加すべき検証

最低限、CI で以下を自動テストする。

- `id` が全件 unique
- `speed`, `spin`, `control` が整数 1〜5
- `price` は `null` または 0 より大きい有限数
- `priceLabel` と `price` の矛盾検査
- `source` は `https:`
- source domain が許可済みメーカーか
- `styles` が空でない
- `brand` と `brandTint` の網羅性
- `verifiedAt` が有効な ISO 日付
- 特定ガイドで参照する ID が実在

### セキュリティ上の意味

現在 `source` はコード内定数なので危険度は低いが、将来データを外部入力化した場合に `javascript:` 等を通さない基盤になる。

## ROB-01 — localStorage の型検証不足

**優先度: P2 / Medium**

### 現状

```ts
JSON.parse(raw) as T
```

としており、JSONとして読めても構造が壊れているケースを検出しない。

例:

- favorite rubbers が object
- favorite sets の field 欠損
- 古いバージョンの schema

などで、後続の `.includes()` / `.some()` / 日付処理等が例外になる可能性がある。

### 修正設計

- Zod を残すなら schema validation に利用
- Zod を依存整理で削除するなら軽量 type guard を実装
- 不正データは破棄して既定値へ戻す
- schema version を明示
- migration が必要な場合のみ旧データを変換

### 完了条件

localStorage に異常値を入れても画面がクラッシュしない。

## ARCH-01 — 不要なサーバー・テンプレート資産

**優先度: P2 / Medium**

### 現状

RubberDB は GitHub Pages の静的配信にもかかわらず:

- Express
- ManusDialog
- Map
- 多数の shadcn/Radix UI wrapper
- 多数の未使用 npm dependencies

`package.json` の `build` も Vite 後に Express server を esbuild する設計だが、Pages workflow は直接 `vite build` を呼び、server bundle を使っていない。

### 問題

- 依存脆弱性の母数増加
- lockfile肥大化
- build / upgrade コスト増
- 実際に必要なコードの把握が難しくなる

### 修正設計

- `server/` 削除
- Express 削除
- unused component 削除
- unused dependency 削除
- build script を静的 build に一本化

将来 server deploy の可能性を残すなら、別 package / workspace として切り離す。

## SEC-06 — CSP 等のブラウザ防御

**優先度: P2 / Medium（Defense in Depth）**

### 現状

Pages artifact の HTML 内には CSP 指定がない。

GitHub Pages が返す実際のレスポンスヘッダーは今回未確認。

### 修正設計

まず本番 URL の response headers を確認する。

CSP がない場合、GitHub Pages では任意レスポンスヘッダー設定が難しいため、必要に応じて `<meta http-equiv="Content-Security-Policy">` を検討する。

現行構成で Analytics を削除するなら、比較的厳しい CSP を設計しやすい。

例として検討する directive:

- `default-src 'self'`
- `script-src 'self'`
- `style-src 'self' 'unsafe-inline'`（Tailwind/既存実装との整合を確認）
- `img-src 'self' data:`
- `connect-src 'self'`
- `object-src 'none'`
- `base-uri 'self'`

注意: meta CSP には response header CSP と異なる制限があり、`frame-ancestors` 等は使えないため、実装前に仕様確認する。

# 6. セキュリティ上「問題なし／良い」と確認した点

今回確認した範囲では以下は良好。

- 本番 RubberDB は基本的に静的サイト
- ユーザー認証・セッション Cookie・サーバーDBを持たない
- `rubberData.ts` のテキストは React により通常の text node として描画
- 主要画面でユーザー入力を HTML として直接挿入する実装は確認していない
- 外部メーカーリンクは `target="_blank"` と `rel="noreferrer"` を使用
- `.env`, `.env.local`, `.env.*.local` は `.gitignore` 対象
- 最新 Pages artifact を典型的な秘密鍵/APIトークンパターンで確認した範囲では、ハードコードされた credential は検出していない
- `tsconfig.json` は `strict: true`
- GitHub Actions は `pnpm install --frozen-lockfile` を利用
- 本番 bundle には未使用 Map / Forge API key / Axios の文字列は確認されず、現在の主要実行経路には入っていないと判断できる

### 補足

これは「リポジトリ全履歴に秘密情報が一度も存在しなかった」ことを保証するものではない。履歴全体の secret scanning は別途 GitHub Secret Scanning 等で実施する。

# 11. 最終判定

## 本番サイト

**現状の公開サイトを直ちに停止する必要があるレベルの問題は確認していない。**

ただし、Analytics と favicon はすでに本番成果物上で不正な参照が確定しているため、次回修正で対応すべき。

価格ロジックはサイトの推薦・比較結果の信頼性に直接関係するため、同じく次回修正対象とする。

## 開発環境

**Vite 7.1.9 + `--host` は優先対応が必要。**

特に Windows を含む LAN 公開型の開発では、確認済み Vite Advisory の影響条件に合致するため、Vite 更新と localhost 限定を最優先とする。

## 推奨方針

RubberDB は機能的に静的サイトで完結しているため、**「静的サイトとして必要なコード・依存だけ残す」方向へ整理するのが、セキュリティ・保守性・CI速度の全てで最も効果が高い。**
